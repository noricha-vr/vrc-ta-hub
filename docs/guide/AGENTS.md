# docs/guide の書き方（使い方ガイド）

`/guide/` に出るマニュアルの本文。ここを触る時（ページの追加・更新・画像の撮り直し）は、このファイルの決まりに従う。

## 読者

- **Discord も VRChat も始めたばかりで、ほとんど何も分からない人**を読者にする
  - 集会（VRChat の中で定期的に開かれる勉強会・交流会）を始めたい主催者、手伝いを頼まれたスタッフ、発表（LT）を頼まれた人
  - 「サーバー」「チャンネル」「ロール」「Webhook」「インスタンス」「グループ」の意味を知らない前提で書く
  - スマホで読むことも多い。PC の前で、ガイドを横に開きながら操作する人も多い
- 読み終えた時に「次に何を押せばいいか」が分かっていることをゴールにする。仕組みの説明は最小限にし、手順と結果を書く

## 書き方

- 文体は「です・ます」。1 文を短く（目安 40 文字）。1 段落 3 文まで
- 画面に出る言葉（ボタン名・項目名・メニュー名）は **画面の表記どおり** に「」で囲む。違う呼び方をしない（例: 画面が「集会一覧」なら「マイ集会」と書かない）
- 専門用語は、そのページで最初に出た時に一言で説明するか、[用語集](glossary.md) へリンクする
  - 例:「Webhook（ウェブフック。Hub から Discord のチャンネルへ自動でお知らせを送るための URL）」
- 「〜できます」で終わらせず、どこを押すかまで書く。「適宜」「必要に応じて」は使わない
- 主催者だけができる操作は、ページの冒頭に「この操作は主催者だけができます」と書き、`_nav.yaml` に `owner_only: true` を付ける
- 内部リンクは `../event/create.md` のような **相対パスの .md** で書く（テストがリンク切れを検出する）。外部リンクは https の完全な URL
- 公開リポなので、運営の内部事情・本番インフラの状態・未告知のイベント名や日程を書かない

## 1 ページの型

手順を含むページは、この順番で書く。

```markdown
---
title: 集会を登録する            # 画面・目次に出る名前。動詞で終える
description: 120 文字以内の説明    # 検索結果と OG 画像に使う
---

# 集会を登録する

（1〜2 文で「このページでできること」と「終わるとどうなるか」）

## 始める前に

- 必要なもの（アカウント、権限、用意する画像や URL など）
- かかる時間の目安（分かる時だけ）

## 手順

### 1. 〇〇を開く

（何をするかを 1〜3 文）

![「集会を追加」ボタンの位置を赤枠で示した画面](images/community/create-01.webp)

① の「集会を追加」を押します。

### 2. 〇〇を入力する
...

## うまくいかない時

### 〇〇と表示される
（原因と、どうすれば直るか）

## 次にやること

- [イベントを登録する](../event/create.md)
```

- **1 手順に 1 枚以上の画像**を付ける。画像の無い手順を作らない（Discord など Hub の外の操作は「Discord の画面」節を参照）
- 手順の見出しは「番号. 動詞」（「1. 集会設定を開く」）。見出しの下に手順を長く書かない。1 手順で押すボタンは 1〜3 個まで。多い時は手順を分ける
- 入力項目が多い画面は、表（項目 / 何を入れるか / 必須か）にまとめる
- 1 ページが長くなりすぎたら（目安: 手順が 8 個超）、ページを分ける
- 手順の無い説明ページ（はじめに・用語集・よくある質問）は、この型に従わなくてよい

## 画像

### 置き場と名前

- 置き場: `app/guide/static/guide/images/<セクション>/`（セクションは docs/guide のディレクトリ名と同じ）
- 名前: `<ページ名>-<2桁の番号>.webp`。スマホ幅は `<ページ名>-<2桁の番号>-sp.webp`
  - 例: `docs/guide/community/create.md` の 1 枚目 → `images/community/create-01.webp`
- 形式は WebP。PC 幅は横 1280px で撮り、必要な部分だけを切り出す

### 本文での書き方

```markdown
![「集会を追加」ボタンの位置を赤枠で示した画面](images/community/create-01.webp)

① の「集会を追加」を押します。
```

- パスは `images/...` から書く（`/static/...` や `https://data.vrc-ta-hub.com/...` を直書きしない）。表示時に view が配信先の URL に書き換える。テストは `app/guide/static/guide/images/` に実ファイルがあるかを見る
- **alt は必須**。「画面」「スクリーンショット」だけにせず、何が写っていて、どこに印があるかを書く（画像が見えない人が alt だけで手順を追えるように）
- キャプションは画像の直後の段落に書く（`figure` / `figcaption` はサニタイズで消える）。画像の中の ① ② と本文の ① ② を対応させる

### 撮り方

- 撮影は `scripts/guide_screenshots/` のスクリプトで行い、手で撮った画像を置かない（後で全部撮り直せるようにする）。使い方は `scripts/guide_screenshots/README.md`
- 撮るのはデモ用のデータ（スクリプトが SQLite に毎回作るもの）だけ。ローカルの MySQL や本番のデータを写さない
- 押す場所は赤い枠と、枠の右上の赤い丸の番号で示す（本文では ① ② と書いて対応させる）。枠はスクリプトが撮影直前にページへ重ねて描く
- 操作の多い画面（フォーム・メニュー）は、スマホ幅（横 390px）も撮る
- **本文には PC 版の画像だけを書く**。同じ番号の `-sp.webp` があれば、スマホ幅では表示側が自動でそちらに差し替える（同じ画面を 2 枚並べない。「スマホでは〜」の段落も、操作が PC と違う時だけ書く）

### 個人情報・秘密情報

- 写してはいけないもの: 実在の人のメールアドレス・Discord ID・Webhook URL・API キー・トークン・パスワード・実在のユーザー名
- デモデータは `example.com` のメールアドレスと架空の名前だけで作る。Webhook URL・API キーはダミー値を入れ、画面に出る時はスクリプトで伏せる
- スクリプトは撮影前に表示テキストと入力値を検査し、`@example.com` 以外のメールアドレス・17〜19 桁の数字（Discord ID）・ダミー以外の Webhook URL・鍵形式の文字列が見つかったら撮らずに止まる。それでも最後に全部の画像を目で確認する

### Discord の画面

- 本物の Discord アカウントで撮らない（自分のサーバー名やフレンドが写るため）
- Discord 側の操作（Webhook の作成、開発者モード、ロール ID のコピーなど）は、`scripts/guide_screenshots/` の HTML モックを撮影して図にし、本文に「（画面はイメージです）」と書く。ボタン名は実際の Discord の日本語表記に合わせる

## 目次と表に残すもの

- 新しいページは `_nav.yaml` に足す。目次にないページを作らない（テストが検出する）
- `_coverage.md`: 利用者が触る画面とガイドのページの対応表。画面やページを増やしたら更新する
- `_review.md`: UI/UX のレビュー指摘と対応の記録
- `AGENTS.md` と `_` で始まるファイルは `/guide/` に出ない（view が 404 を返す）

## 確認と本番反映

- テスト: `docker compose exec vrc-ta-hub python manage.py test guide`（リンク切れ・画像切れ・alt の空・目次と実ファイルの食い違いを検出する）
- 画面での確認: ローカルの `/guide/` を PC 幅とスマホ幅で見る
- 画像は本番では Cloudflare R2 から配信され、デプロイでは上がらない。**画像を足した PR はマージ前に** `DEBUG=False` の collectstatic で R2 に上げる（`.claude/rules/staticfiles-deployment.md`）
